### 3. Анализ NATS JetStream интеграции ✅

#### JetStream компоненты:

**KV Buckets** (используются для метаданных):
- `koldun_models` - реестр моделей (namespace/name → Model metadata)
- `koldun_tokens` - реестр токенов (hash → Token metadata)
- `koldun_ttl` / ConversationKV - conversation records с TTL

**Streams** (используются для очередей):
- `KOLDUN_LLM_REQUESTS` - backlog запросов
- `sessions.<hash>.requests` - per-session backlogs
- `SESS_<HASH>_STATE` - worker heartbeat events

**Assignments Bucket**:
- `sess_<hash>_assign` - dispatcher assignment tracking

#### Реализация:

```go
// pkg/controllers/registry.go
type registrySync struct {
    modelsKV nats.KeyValue  // koldun_models bucket
    tokensKV nats.KeyValue  // koldun_tokens bucket
}

// pkg/controllers/conversation_controller.go
type conversationHandler struct {
    kv nats.KeyValue  // koldun_ttl bucket
}
```

#### Conversation Flow валиден:
1. ✅ Backend → JetStream KV (`nats_ttl_<hash>`)
2. ✅ Operator watches KV → ensures Session/Dllama
3. ✅ Dispatcher reads backlog → assigns to workers
4. ✅ LLM workers → dllama-api → streams to `out.<hash>`

#### TTL Management:
Префикс `nats_ttl_` используется для автоматической очистки неактивных сессий через JetStream TTL механизм.

## Архитектурные insights

### Сильные стороны:
1. **Separation of concerns**: Чёткое разделение на CRD, Controllers, Servers
2. **Wrangler integration**: Правильное использование OnChange/OnRemove handlers
3. **NATS-first**: JetStream используется как single source of truth для метаданных
4. **Idempotency**: Assignment buckets предотвращают duplicate processing

### Потенциальные риски:
1. **NATS single point of failure**: Нет fallback механизмов при потере NATS
2. **Bucket naming collisions**: `sess_<hash>_assign` ограничен 63 символами (truncation)
3. **TTL management**: Зависимость от JetStream TTL для cleanup (нет явного GC)
