### Почему это критично

#### 1. Dispatcher Server (~10KB)
**Назначение**: Координация распределения задач между воркерами через NATS
**Риски без тестов**:
- Некорректное распределение нагрузки
- Потеря сообщений из backlog
- Race conditions в worker state management
- Утечки памяти в inflight assignments
- Ошибки при requeue сообщений

**Критичные функции без покрытия**:
```go
- handleBacklog()      // обработка очереди задач
- handleState()        // обработка состояния воркеров
- selectWorker()       // выбор воркера для задачи
- recoverAssignments() // восстановление после сбоев
```

#### 2. Ingress Server (~47KB) 
**Назначение**: OpenAI-совместимый API endpoint, основной точка входа
**Риски без тестов**:
- Некорректная обработка API запросов
- Проблемы с authentication/authorization
- Утечки данных через streaming responses
- Проблемы с CORS
- Ошибки маршрутизации по conversation hash

**Критичные функции без покрытия**:
```go
- handleChatCompletion()     // основной API endpoint
- validateToken()            // проверка токенов
- resolveModel()             // разрешение имён моделей
- streamResponse()           // стриминг ответов
- conversationHashFromHeaders() // маршрутизация
```

#### 3. LLM Server (~26KB)
**Назначение**: Sidecar для distributed-llama, обработка inference
**Риски без тестов**:
- Некорректная обработка inference requests
- Проблемы с NATS messaging
- Ошибки в worker state reporting
- Memory leaks в long-running процессах

**Критичные функции без покрытия**:
```go
- handleIncoming()     // обработка входящих запросов
- publishState()       // публикация состояния
- executeInference()   // запуск inference
```

### Влияние на систему

#### Производственные риски
1. **Невозможно уверенно рефакторить** - любые изменения могут сломать функциональность
2. **Нет защиты от регрессий** - баги могут вернуться незамеченными
3. **Сложно отлаживать** - нет воспроизводимых тестовых сценариев
4. **Опасно деплоить** - нет автоматической валидации критичных путей

#### Примеры потенциальных проблем
- **Data loss**: Сообщения могут теряться при ошибках NATS publish
- **Deadlocks**: Race conditions в dispatcher worker state
- **Auth bypass**: Проблемы в token validation
- **Memory leaks**: Незакрытые NATS subscriptions

## 🚨 КРИТИЧЕСКАЯ НАХОДКА #2: Недостаточная обработка ошибок NATS

### Обнаружено при анализе кода

При исследовании серверных компонентов выявлен **паттерн слабой обработки ошибок**:

#### Проблемный паттерн
```go
// ❌ ПЛОХО: Ошибка только логируется, никаких действий
if err := s.nc.Publish(subject, payload); err != nil {
    s.log.WithError(err).Warn("publish assignment")
    return  // Операция молча проваливается!
}

if _, err := s.assignments.Put(backlog.ID, payload); err != nil {
    s.log.WithError(err).Warn("record assignment kv")
    // Продолжаем выполнение, хотя данные не сохранены!
}
```

### Найденные случаи в dispatcher/server.go

| Строка | Проблема | Последствие |
|--------|----------|-------------|
| 196 | `nc.Publish()` - только Warn | Потеря сообщений backlog |
| 215 | `nc.Publish()` - только Warn | Потеря assignments |
| 220 | `assignments.Put()` - только Warn | Нет записи в KV store |
| 300 | `assignments.Delete()` - только Warn | Утечка данных в KV |
| 316 | `nc.Publish()` - только Warn | Потеря при republish |
| 352 | `assignments.Get()` - только Warn + continue | Пропуск данных |
| 366 | `assignments.Delete()` - только Warn | Утечка при cleanup |

### Найденные случаи в ingress/server.go

| Строка | Проблема | Последствие |
|--------|----------|-------------|
| 295 | `startStateObserver()` - только Warn | Нет мониторинга состояния |
| 549 | Token validation - только Warn | Слабая безопасность |
| 558 | Read body - возврат 400, но нечёткий лог | Сложно отлаживать |

### Почему это критично

#### 1. Потеря данных
- Сообщения из backlog могут теряться при ошибках NATS
- Assignments не сохраняются в KV store
- Нет механизма повторных попыток

#### 2. Inconsistent state
- KV store может рассинхронизироваться с реальным состоянием
- Inflight assignments могут "зависнуть"
- Воркеры могут не получить задачи

#### 3. Нет observability
- Невозможно понять, насколько часто происходят ошибки
- Нет метрик для мониторинга
- Сложно диагностировать проблемы в production
