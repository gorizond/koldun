# Koldun Platform - Итеративная отладка и развитие

## Циклическое техническое задание (ЦТЗ)

Этот документ — живое циклическое ТЗ: каждая новая сессия обязана стартовать с чтения файла, актуализировать состояние (через `next_session`) и вернуть изменения обратно сюда. Цикл выглядит так:
1. **Старт с Фазы 0** — перечитываем `next_session`, историю и необходимые гайды перед началом работы.
2. **Рабочая итерация** — выполняем задачи, фиксируем артефакты, обновляем инструкции в процессе (если появляются новые правила или ограничения).
3. **Хандофф** — завершаем отчёт, обновляем блок `next_session` и при необходимости расширяем это ЦТЗ, чтобы следующий запуск не требовал дополнительных вопросов.
4. **Немедленный перезапуск** — после фиксации отчёта сразу стартуем новую сессию, берём свежий `next_session` и повторяем шаги 1-3. Никаких пауз или ожиданий подтверждения, цикл идёт непрерывно (если `status: ready`; при `blocked` сначала запрашиваем недостающие данные).

Если выявлены новые обязательные шаги/гайды, они должны быть добавлены в этот файл, чтобы сохранить непрерывность цикла. Любая новая LLM или разработчик просто подключается, читает `context/0_REASONING_TASK.md` и продолжает цикл «ТЗ → реализация → обновление ТЗ», не теряя накопленный контекст.

## ⚠️ КРИТИЧЕСКИ ВАЖНО - Управление контекстом LLM

### Для ЛЮБОЙ LLM (Claude Code, ChatGPT, Claude API, и т.д.)

**ВСЕГДА ПРИКРЕПЛЯЙТЕ ТОЛЬКО ЭТОТ ФАЙЛ (`context/0_REASONING_TASK.md`) В КОНТЕКСТ!**

**❌ НИКОГДА НЕ ПРИКРЕПЛЯЙТЕ ФАЙЛЫ СЕССИЙ:**
- ❌ `iterations/2025-11-01_01-20_session_2.md`
- ❌ `iterations/YYYY-MM-DD_HH-MM_session_N.md`
- ❌ Любые другие файлы из папки `iterations/`

**Почему это критично:**
1. **Файлы сессий огромные** - быстро забивают token budget (часто >50000 токенов)
2. **Мастер-план достаточен** - содержит всю необходимую информацию для старта
3. **LLM сам найдёт нужное** - имеет инструменты `Read`, `Glob`, `Grep` для чтения файлов
4. **Экономия контекста** - больше места для рабочего кода и анализа

**Правильный workflow для разных LLM:**

**Claude Code:**
1. Открыть новый чат
2. Прикрепить **ТОЛЬКО** `context/0_REASONING_TASK.md`
3. Написать: "продолжи работу" или "проверь незавершённые сессии"
4. LLM автоматически найдёт и прочитает нужные файлы сессий

**ChatGPT / Claude Web / другие web-интерфейсы:**
1. Открыть новый чат
2. Прикрепить **ТОЛЬКО** `context/0_REASONING_TASK.md`
3. Написать запрос с контекстом
4. LLM будет использовать мастер-план как основу

**API (Claude API / OpenAI API):**
```python
# Читать ТОЛЬКО мастер-план
with open("context/0_REASONING_TASK.md") as f:
    master_plan = f.read()

messages = [
    {"role": "system", "content": master_plan},
    {"role": "user", "content": "продолжи работу"}
]
```

**Как LLM находит файлы сессий автоматически:**
- LLM читает правило "Фаза 0: Проверка незавершённых сессий"
- Использует `Glob` для поиска `context/iterations/*.md`
- Читает последние файлы с помощью `Read`
- Продолжает работу с нужным контекстом
- **Вам НЕ нужно делать это вручную!**

## Метаинформация проекта
- **Платформа**: Kubernetes-ориентированная система для распределённого выполнения LLM
- **Архитектура**: OpenAI-совместимый API → NATS JetStream → Distributed LLaMA
- **Основной язык**: Go 1.21+
- **Оркестратор**: Kubernetes с Wrangler-контроллерами

## Основные компоненты системы

### 1. Custom Resources (CRD)
- `Session` - управление диспетчерами и пулами Dllama
- `Dllama` - топология distributed-llama для конкретной модели
- `Model` - загрузка, конвертация и управление артефактами моделей
- `Root` - координатор distributed-llama (Deployment)
- `Worker` - рабочие узлы StatefulSet
- `Ingress` - публичная точка входа и backend

### 2. Режимы работы бинарника (`cmd/operator`)
- `operator` - контроллеры и синхронизация с JetStream
- `backend/ingress` - OpenAI HTTP API, валидация токенов
- `dispatcher` - распределение запросов между воркерами
- `llm` - sidecar для dllama-api процессов

### 3. Внешние зависимости
- NATS JetStream (KV buckets, streams)
- Object Storage (S3/MinIO) для моделей
- Kubernetes CSI для PVC

## Цикл итеративной работы

### Фаза 0: Проверка незавершённых сессий (ОБЯЗАТЕЛЬНО!)
```yaml
КРИТИЧЕСКИ ВАЖНО: При каждом запуске работы ПЕРВЫМ ДЕЛОМ проверить наличие незавершённых сессий!

actions:
  - Если текущий чат содержит только этот файл, самостоятельно прочитать самый свежий отчёт из context/iterations/
  - Проверить файлы в context/iterations/ отсортированные по дате
  - Найти последнюю сессию и проверить её статус
  - Если статус != "Завершено ✅", ПРОДОЛЖИТЬ эту сессию
  - НЕ создавать новые отчёты/сессии если есть незавершённая работа
  - Прочитать план из незавершённой сессии
  - Не запрашивать подтверждение у пользователя: решение принимается на основе отчётов в iterations/
  - Если незавершённых сессий нет, прочитать блок `next_session` из последнего отчёта и использовать его как стартовый план
  - Продолжить с того места где остановились
  - Убедиться, что в `next_session.todo` первой строкой стоит задача по тестированию/покрытию

outputs:
  - Решение: продолжить существующую сессию ИЛИ начать новую
  - Контекст незавершённой работы (если есть)
  - План действий для продолжения

ВАЖНО: Это предотвращает дублирование работы и потерю контекста!

context_management:
  КРИТИЧЕСКОЕ ПРАВИЛО - Управление контекстом LLM чата:
  - После завершения логического этапа работы (например, создание одного модуля)
  - При достижении ~45-50% использования token budget
  - После успешного коммита изменений
  - НЕМЕДЛЕННО выполнить автоматический handoff через Agor MCP:
    1. Создать отчёт сессии с next_session блоком
    2. Обновить INDEX.md
    3. Запустить новую сессию через `mcp__agor__agor_sessions_prompt` с mode="fork":
       "действуй согласно циклическому ТЗ context/0_REASONING_TASK.md"
    4. НЕ ЖДАТЬ подтверждения пользователя - автоматический перезапуск цикла

  Причины:
  - Предотвращение переполнения контекста
  - Улучшение качества ответов LLM
  - Снижение латентности и стоимости запросов
  - Фокусировка на текущей задаче без "хвоста" истории
  - **Непрерывность цикла без участия пользователя**

  Автоматический fork через Agor MCP:
  ```
  mcp__agor__agor_sessions_prompt({
    sessionId: "<parent_or_root_session_id>",  // ВАЖНО: форкать от РОДИТЕЛЬСКОЙ сессии, не от текущей!
    prompt: "действуй согласно циклическому ТЗ context/0_REASONING_TASK.md",
    mode: "fork",
    title: "Session N+1 — Продолжение цикла",
    agenticTool: "claude-code",
    permissionMode: "bypassPermissions"
  })
  ```

  **КРИТИЧЕСКИ ВАЖНО**: Всегда форкать от **родительской/корневой сессии**, а НЕ от текущей!
  - Используй `mcp__agor__agor_sessions_get_current()` чтобы получить `forked_from_session_id` или `parent_session_id`
  - Если текущая сессия была форкнута (`forked_from_session_id` != null), форкай от той же сессии
  - Это создаёт **плоскую структуру siblings**, а не цепочку вложенных форков

  **ROOT SESSION ID для worktree optimize:**
  ```
  f8fcd382-cbd8-42db-a47c-43b53f06596b
  ```
  Эта сессия имеет `parent_session_id: null` и `forked_from_session_id: null` — корень всех циклических итераций.
  Все новые форки должны идти **от этой сессии** чтобы создать плоскую структуру.

  **Пример правильного форка:**
  ```typescript
  // 1. Получить текущую сессию
  const current = await agor_sessions_get_current();
  // current.session_id = "6366ac84"
  // current.genealogy.forked_from_session_id = "f538db43"  <-- РОДИТЕЛЬ!

  // 2. Форкать от РОДИТЕЛЬСКОЙ сессии (НЕ от текущей!)
  await agor_sessions_prompt({
    sessionId: "f538db43",  // <-- forked_from_session_id, НЕ current.session_id!
    prompt: "действуй согласно циклическому ТЗ context/0_REASONING_TASK.md",
    mode: "fork",
    permissionMode: "bypassPermissions"
  });
  // Результат: новая сессия будет SIBLING к текущей (оба форкнуты от f538db43)
  ```

  **Алгоритм поиска ROOT сессии (если genealogy глубокая):**
  ```typescript
  // Если нужно найти КОРНЕВУЮ сессию (не просто родителя):
  async function findRootSession(): Promise<string> {
    let current = await agor_sessions_get_current();
    let rootId = current.session_id;

    // Подниматься по цепочке пока есть родитель
    while (current.genealogy.forked_from_session_id || current.genealogy.parent_session_id) {
      const parentId = current.genealogy.forked_from_session_id || current.genealogy.parent_session_id;
      current = await agor_sessions_get(parentId);
      rootId = current.session_id;
    }

    return rootId;  // Сессия без родителей = root
  }

  // Использование:
  const rootId = await findRootSession();
  await agor_sessions_prompt({
    sessionId: rootId,  // <-- ROOT сессия, все форки будут siblings первого уровня
    mode: "fork",
    ...
  });
  ```

  **НЕПРАВИЛЬНО** (создаёт глубокую вложенность):
  ```typescript
  // НЕ ДЕЛАЙ ТАК! Это создаёт цепочку форков
  await agor_sessions_prompt({
    sessionId: current.session_id,  // "6366ac84" <-- ТЕКУЩАЯ сессия = НЕПРАВИЛЬНО!
    mode: "fork"
  });
  // Результат: новая сессия будет CHILD к текущей (вложенность растёт)
  ```

  Это обеспечивает:
  - Форк от общей родительской сессии (все форки — siblings на одном уровне)
  - Сохранение worktree контекста
  - Непрерывность итеративного процесса
  - Свежий контекст для каждой сессии
  - **Плоская структура сессий без глубокой вложенности** — все форки от одного родителя
  - **Автономная работа без запросов разрешений** (bypassPermissions)
```

**Известные ограничения:**
- kubectl logs timeout (TLS handshake) — сетевая проблема Rancher Desktop VM
- MinIO без persistence (данные теряются при restart)
- NATS с memory storage (не для production)

**Правила для LLM агентов:**
- **НИКОГДА не использовать sleep > 60 секунд** между задачами для ожидания результатов
- Если процесс долгий (сборка, загрузка), проверять статус каждые 30-60 секунд
- При длительных операциях фиксировать промежуточный прогресс и переходить к следующим задачам
- Не блокировать контекст бесконечным ожиданием - лучше зафиксировать состояние и продолжить в следующей сессии

**КРИТИЧЕСКИ ВАЖНО: CPU Inference и NATS очереди:**
- **CPU inference ОЧЕНЬ медленный** (минуты на один запрос) - не делать множественные запросы
- **НИКОГДА не отправлять несколько запросов в один root-0 pod** - это вызовет timeout
- **Использовать NATS очереди** для управления нагрузкой, они созданы именно для этого
- **ВСЕГДА мониторить нагрузку** перед отправкой запросов:
  - Проверить NATS backlog: `kubectl exec koldun-nats-0 -c nats -- nats stream info`
  - Проверить LLM sidecar в root pod: `kubectl logs <root-pod> -c llm`
  - Проверить активные запросы через dispatcher logs
- **Один запрос за раз** на локальной машине - дождаться завершения перед следующим
- При timeout ошибке - НЕ повторять запрос сразу, проверить состояние системы

## Автоматический handoff между сессиями

Каждый отчёт в `iterations/*.md` завершается блоком:
```yaml
next_session:
  status: ready            # ready | blocked
  summary: >-
    Краткое напоминание о достигнутом результате
  todo:
    - Перечень задач, которые нужно выполнить в следующей сессии (в порядке приоритета)
  blockers:
    - Что препятствует продолжению (если есть)
  context_files:
    - Путь_к_файлу:комментарий  # Какие файлы перечитать перед стартом
```

- `status`: `ready`, если можно продолжать автономно; `blocked`, если нужна обратная связь пользователя (указывать причину в `blockers`).
- При запуске новой сессии автоматически использовать последний блок `next_session` вместо уточняющих вопросов пользователю.
- После выполнения задач обновлять блок `next_session`, чтобы обеспечить непрерывность работы.

## Правила именования файлов итераций

Файлы сессий должны сохраняться в папке `iterations/` со следующим форматом имени:
- **Формат**: `YYYY-MM-DD_HH-MM_session_N.md`
- **Пример**: `2025-11-01_14-30_session_1.md`
- **Где**:
  - `YYYY-MM-DD` - дата проведения сессии
  - `HH-MM` - время начала сессии (24-часовой формат)
  - `N` - порядковый номер сессии в этот день

Это позволяет:
- Точно отслеживать хронологию работы
- Избегать конфликтов при множественных сессиях в день
- Легко находить конкретную сессию по времени

## Автоматическое обновление INDEX.md

**КРИТИЧЕСКИ ВАЖНО**: После создания ЛЮБОЙ новой сессии в `iterations/` LLM ОБЯЗАН обновить [iterations/INDEX.md](iterations/INDEX.md)!

### Процедура обновления INDEX.md

1. **После создания файла сессии** (например, `2025-11-08_14-11_session_1.md`):
   ```yaml
   actions:
     - Прочитать только что созданный файл сессии
     - Извлечь ключевую информацию:
       * Дату и время (из имени файла)
       * Заголовок сессии (первая строка markdown)
       * Фокус работы (из метаданных)
       * Итерацию (если применимо)
     - Открыть iterations/INDEX.md
     - Добавить новую запись в соответствующий раздел итерации
     - Обновить статистику в конце файла
     - Обновить timestamp "Последнее обновление"
   ```

2. **Формат записи в INDEX.md**:
   ```markdown
   ### [YYYY-MM-DD_HH-MM_session_N](YYYY-MM-DD_HH-MM_session_N.md)
   **Заголовок сессии**
   - Краткое описание фокуса работы (1-2 строки)
   - Ключевые достижения (если есть milestone)
   ```

3. **Обновление статистики**:
   ```markdown
   **Всего сессий**: N  (увеличить на 1)
   **Последнее обновление**: YYYY-MM-DD HH:MM  (текущее время)
   **Обновлено автоматически**: ✅
   ```

### Пример автоматического обновления

**Ситуация**: Только что создана сессия `2025-11-08_14-11_session_1.md`

**Действия LLM**:
1. Прочитать новый файл сессии
2. Открыть `iterations/INDEX.md` с помощью `Read`
3. Использовать `Edit` для добавления новой записи:
   ```markdown
   ### [2025-11-08_14-11_session_1](2025-11-08_14-11_session_1.md)
   **Сессия 1 — Решение проблемы зависания тестов с coverage**
   - ⚠️ Проблема: t.Parallel() + coverage deadlock
   - ✅ Решение: удалены все t.Parallel() (257 строк)
   - ⚠️ Envtest временно отключен
   ```
4. Обновить статистику: `**Всего сессий**: 47` (было 46)
5. Обновить timestamp: `**Последнее обновление**: 2025-11-08 14:11`

### Проверка автообновления

После каждой сессии проверить:
- ✅ Новая запись добавлена в INDEX.md
- ✅ Запись находится в правильной итерации
- ✅ Статистика обновлена
- ✅ Timestamp актуален
- ✅ Формат записи соответствует шаблону

**ВАЖНО**: Если LLM забыл обновить INDEX.md, пользователь может напомнить: "обнови INDEX.md"
